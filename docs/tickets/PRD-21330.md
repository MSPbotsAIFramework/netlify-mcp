## Product design

### Goals / Non-goals

**Goals:**
- Ship a first version of `MSPbotsAIFramework/netlify-mcp` that lets an AI agent, acting on behalf of one MSPbots tenant's own Netlify personal access token, manage the five capability areas the requester was already told this connector covers:
  - **Sites**: list/get existing sites, create a new (non-git-linked) site, update basic site settings, delete a site on confirmation.
  - **Deploys**: list/get a site's deploy history and each deploy's build state, roll back (restore) a site to a previous deploy on confirmation.
  - **Environment variables**: list/get/create/update-one-value/delete environment variables, scoped to either one site or the caller's whole team (account), matching Netlify's own two-level model.
  - **Forms**: list a site's forms and their submissions, moderate a submission (mark spam/verified), delete a submission or a whole form on confirmation.
  - **DNS**: list/get/create/delete DNS zones and the records inside them.
- Every call authenticates with the caller's own Netlify personal access token carried as one request header; one running server instance safely serves multiple MSPbots tenants' Netlify accounts concurrently (same multi-tenant, stateless, header-credential isolation contract as every other first-party MCP in this org).

**Non-goals (this version):**
- **Creating a brand-new deploy from a file bundle** (`POST /sites/{id}/deploys` with a zip or file-digest manifest) is out of scope: it is a multi-step upload protocol (digest manifest → per-file PUT of changed files) unsuited to a single JSON-RPC tool call with a size-capped response, and is not how Netlify expects most integrations to trigger builds anyway (that is normally done via their own git integration or a build hook URL). `netlify_restore_deploy` (rollback to an existing, already-built deploy) covers the "change what's live" need this ticket's template implies without requiring a file-upload protocol.
- **Full git-linked site creation** (wiring a new site to a GitHub/GitLab/Bitbucket repo with `build_settings.cmd`/`dir`/`repo_branch`) is out of scope for `netlify_create_site`; v1 creates a plain site (optionally with a custom domain) that an operator can wire to a repo afterward in the Netlify UI. Reason: repo-linking requires an OAuth installation step on Netlify's side that a bare personal-access-token call cannot complete.
- **Batch/multi-value environment-variable operations** (`updateEnvVar`'s full-array replace, `deleteEnvVarValue`'s single-value-row delete) are not exposed; `netlify_set_env_var_value` (upsert one context's value) and `netlify_delete_env_var` (delete the whole key, every context at once) cover the common agent workflows of "add/change a setting" and "remove a setting" without a second tool per edge case.
- **Site metadata, build hooks/webhooks, deploy snippets, and SSL provisioning** endpoints exist in Netlify's API but are not named by this ticket's five areas (sites/deploys/env vars/forms/DNS) and are left for a follow-up ticket if a concrete need shows up (Risks & dependencies).
- No UI — this is a headless MCP server, same as every other connector in this org.

### Acceptance criteria

- **AC1**: Given a valid `X-Netlify-Token` header, when the agent calls `netlify_test_connection`, then it receives confirmation the token is valid plus the team(s)/account(s) it can act on, with no part of the token echoed back.
- **AC2**: Given a missing or empty `X-Netlify-Token` header, when any tool is called, then the call fails with a structured `unauthorized` error (HTTP 401 at the transport layer) naming the missing header, and no request reaches Netlify.
- **AC3**: Given an existing site, when the agent calls `netlify_list_sites` / `netlify_get_site`, then it receives that site's id, name, URLs, SSL/custom-domain state and basic build settings; an unknown `site_id` returns a structured `not_found` error, not an exception.
- **AC4**: Given the agent wants to create, rename, or delete a site, when it calls the corresponding write tool, then create/update apply immediately, but delete without `confirm: true` is refused with a "not done, confirmation required" result and no call reaches Netlify; `confirm: true` performs the delete.
- **AC5**: Given a site with deploy history, when the agent calls `netlify_list_deploys` / `netlify_get_deploy`, then it receives each deploy's state (e.g. building/ready/error), timestamps, and the commit/branch that produced it, newest first.
- **AC6**: Given a prior deploy on the same site, when the agent calls `netlify_restore_deploy` with `confirm: true`, then that deploy becomes the live production deploy and the response names it; without `confirm: true` it is refused the same way as AC4's deletes.
- **AC7**: Given Netlify responds with its deploy-specific rate limit (3/minute, 100/day), when a restore or list-deploys call is mid-request, then the error returned is `rate_limited` with `retryable: true`, not a crash or a silent hang.
- **AC8**: Given an environment variable flagged `is_secret: true`, when the agent lists or reads it back through this MCP for any context other than `dev`, then the value comes back masked exactly as Netlify itself returns it (this MCP does not attempt to work around Netlify's own masking).
- **AC9**: Given the agent wants to add, change, or remove an environment variable at either the site level or the whole-team level, when it calls the corresponding tool with a valid `account_id`, then the change applies at the level requested (one site, or every site under the team unless a `site_id` scope is given), and delete without `confirm: true` is refused like AC4.
- **AC10**: Given a site with submitted forms, when the agent calls `netlify_list_forms` / `netlify_list_form_submissions` / `netlify_list_site_submissions`, then it receives the forms and/or submissions with their field data, newest first, paginated.
- **AC11**: Given a specific submission, when the agent calls the mark-spam or mark-verified tool, then Netlify's own spam classification for that submission updates accordingly and the response confirms the new state; deleting a submission or a whole form follows the same confirm-gate as AC4.
- **AC12**: Given the caller's account has DNS zones, when the agent calls the DNS zone/record list, get, create, and delete tools, then it can read existing zones/records, add a new zone or record, and delete one only with `confirm: true`; an unknown `zone_id`/`record_id` returns `not_found`.
- **AC13**: Given two different callers' `X-Netlify-Token` values in concurrent requests, when both call any tool at the same time, then neither caller's sites, deploys, env vars, or DNS data become visible to the other — this must hold at the tool/API layer (there is no UI to hide things behind in an MCP server).
- **AC14**: Given any Netlify error response (`{"code": <int>, "message": "<string>"}`), when a tool call fails, then the agent receives this MCP's own structured error envelope (`error.code` one of the fixed six values, `error.message`, `error.retryable`) derived from the HTTP status, never an uncaught exception or Netlify's raw body passed through verbatim.

## Tech design

### Conclusion

Build `MSPbotsAIFramework/netlify-mcp` as a new, from-scratch Python 3.12 + `uv` + FastMCP Streamable-HTTP server (main line A), following the same stateless/multi-tenant/single-header-credential shape `hudu-mcp`, `box-mcp`, `plaid-mcp` and `figma-mcp` all use. Netlify's auth model is the simplest of the four references — one bearer token, no base-URL header needed (unlike Hudu's self-hosted instances) and no second per-call resource token (unlike Plaid's two-tier model) — so the credential surface is a single `X-Netlify-Token` header. The one Netlify-specific wrinkle worth a deliberate decision is pagination: Netlify signals "more results" only through an HTTP `Link` response header, not an in-body cursor or count, so the client has to parse that header rather than reuse any sibling repo's pagination code verbatim (see Data & API contract).

### Option analysis

| Option | What it does | Pros | Cost | Verdict |
|---|---|---|---|---|
| Hand-rolled `httpx` client (same shape as `hudu-mcp`'s `api_client.py`) | Thin per-request client built from the caller's own token; explicit status→error mapping; `Link`-header pagination parser | Matches the house convention already in use by every other first-party MCP here; full control over retry/backoff/error-envelope/pagination shape; no new dependency beyond `httpx` (already standard) | Have to hand-write the `Link`-header parser (Netlify's one real departure from the fleet's usual "count in body" pagination shape) | **Chosen** |
| `pynetlify` / other unofficial community Python clients | Pre-built wrapper over the Netlify API | Saves hand-writing request shapes for 5 resource groups | Netlify does not publish or maintain an official Python SDK (only official JS/Go clients exist); an unofficial third-party wrapper would be an unaudited, possibly unmaintained dependency for something this thin to hand-roll, and would still need to be fought into the same per-request-credential, no-shared-state shape every other MCP here requires | Not chosen: no official SDK exists, and an unofficial one does not offset diverging from the fleet-wide pattern on a repo with no existing code of its own |

No existing code in *this* repo to be consistent with (empty scaffold) — the tie-break is the org-wide house style observed in `hudu-mcp`, not an in-repo precedent.

### Data & API contract

**Credential header** (declared in README, read verbatim in `middleware.py`):

| Header | Required | Meaning |
|---|---|---|
| `X-Netlify-Token` | yes | Netlify personal access token, created at **User settings → Applications → Personal access tokens** in the caller's own Netlify account |

Missing or empty → 401, body names `X-Netlify-Token` (never echoes back what was sent).

**Tools** (31; all return a JSON string; list tools share one pagination envelope):

List envelope: `{"items": [...], "page": int, "per_page": int, "has_more": bool, "next_page": int | null}` — `has_more`/`next_page` parsed from the response's `Link` header (`rel="next"`), not from a body field Netlify does not provide.

1. `netlify_test_connection() -> {"ok": true, "teams": [{"id","name","slug"}]}` — calls `GET /accounts`; the cheapest authenticated call, doubles as a credential check.
2. `netlify_list_accounts() -> {"accounts": [{"id","name","slug","type","created_at"}]}` — `GET /accounts`; used to discover `account_id`/`account_slug` for the tools below that need one.
3. `netlify_list_sites(page=1, per_page=50) -> {items: [{id,name,url,admin_url,ssl_url,custom_domain,state,account_slug,created_at,updated_at}], ...}` — `GET /sites`.
4. `netlify_get_site(site_id: str) -> {...same shape as one item above, plus build_settings: {repo_url,repo_branch,cmd,dir} | null}` — `GET /sites/{site_id}`; unknown id → `not_found`.
5. `netlify_create_site(name: str | None = None, account_slug: str | None = None, custom_domain: str | None = None) -> {site}` — `POST /sites`; `readOnlyHint=false`, `idempotentHint=false` (Netlify assigns a random subdomain name when `name` is omitted, so repeated calls create distinct sites).
6. `netlify_update_site(site_id: str, name: str | None = None, custom_domain: str | None = None, force_ssl: bool | None = None) -> {site}` — `PATCH /sites/{site_id}`; only the provided fields are sent.
7. `netlify_delete_site(site_id: str, confirm: bool = False) -> {"deleted": true} | {"deleted": false, "reason": "confirm_required"}` — `DELETE /sites/{site_id}`; `destructiveHint=true`.
8. `netlify_list_deploys(site_id: str, page=1, per_page=50) -> {items: [{id,state,branch,commit_ref,deploy_url,error_message,created_at,deploy_time}], ...}` — `GET /sites/{site_id}/deploys`, newest first (vendor's own default order).

**Error envelope** (all tools, never an uncaught exception):

```json
{"error": {"code": "not_found", "message": "Netlify returned HTTP 404 for sites/abc123: Site not found", "retryable": false}}
```

`code` is one of the fixed six (`not_configured`/`unauthorized`/`not_found`/`invalid_argument`/`rate_limited`/`upstream_error`). Netlify's own error body is only `{"code": <int>, "message": "<string>"}` (an HTTP-status echo, no vendor-specific taxonomy like Plaid's `error_type`), so the mapping is purely HTTP-status-driven, same shape as `hudu-mcp`'s `_STATUS_TO_CODE` table:

| Netlify HTTP status | MCP `code` | `retryable` |
|---|---|---|
| 400, 409, 422 | `invalid_argument` | false |
| 401, 403 | `unauthorized` | false |
| 404 | `not_found` | false |
| 429 | `rate_limited` | true (honor `Retry-After` if present; deploy endpoints hit this at only 3/min) |
| 5xx, or no HTTP response at all (timeout/connection error) | `upstream_error` | true |

**Backward compatibility**: new repo, no existing tenants depend on a prior tool/header shape — nothing to stay compatible with yet. Future tool/param changes follow SOP §13 (breaking vs. compatible) starting from this version's `tools/list` snapshot.

### Key flow / sequence

Discovering an account and acting on one site's environment variable (representative of the two-level env-var model; every other tool is a single request/response):

```
Agent                         netlify-mcp                            Netlify
  | list_accounts -------------->|
  |                               | GET /accounts ----------------------------> |
  |                               | <----------------------------- [{id,slug}] |
  | <--- accounts ----------------|
  | create_env_var(account_id, ->|
  |   key, values, site_id)       | POST /accounts/{account_id}/env?site_id=.. -> |
  |                               | <----------------------------- env var object |
  | <--- env var ------------------|
```

### Non-functional

- **Idempotency & concurrency**: one shared `httpx.AsyncClient` per process; the credential (`X-Netlify-Token` from the header) travels only through the call stack of its own request — no module-level or cross-request caching. `netlify_create_site` and `netlify_create_dns_zone`/`netlify_create_dns_record` are not idempotent by nature of the vendor API (repeated calls with the same arguments create distinct resources) — documented in the tool descriptions, same honesty Plaid's design gave its own non-idempotent tools.
- **Performance**: `page`/`per_page` clamped to Netlify's own ceiling (`per_page` ≤ 100, default 50 here to keep list responses well under the gateway's size cap); compact (non-pretty) JSON, `ensure_ascii=False`; connect/read timeouts 5s/30s, ≤ 2 retries, whole-call budget under the shared 120s gateway timeout (100s, same margin as `hudu-mcp`). `netlify_restore_deploy` and any deploy-list call are the only tools subject to Netlify's stricter deploy-specific rate limit (3/min, 100/day) — surfaced as `rate_limited`/`retryable=true` (AC7), never retried past the shared call budget regardless of `Retry-After`.
- **Security**: the personal access token is never written to logs — request logging records method/path/status/duration only (same shape as `HuduClient`'s `logger.info` line), never the request or response body. `NetlifyCredentials.__repr__` redacts the token. Secret-flagged environment variable values are never unmasked by this server (AC8) — Netlify itself refuses to return them for any context but `dev`, so there is nothing for this MCP to leak even if it tried. `gitleaks detect` run before the first commit to `main` and again before every subsequent merge.
- **Multi-tenant isolation**: the one credential header is the *entire* identity of a request; nothing about one caller's sites, deploys, env vars, forms, or DNS zones can leak into another caller's response because nothing is ever stored between calls (AC13). Same isolation contract every other MCP server in this org makes.
- **Observability**: one log line per upstream Netlify call (method, path, status, duration, attempt count) — same shape as `hudu-mcp`'s `api_client.py`. No request/response bodies logged, ever (env var values and DNS record values can carry secrets/PII).

### Rollout & rollback

New repo, new vendor — no existing traffic to protect. First version is pushed straight to `main` (SOP A2: "new repo, no one depends on it yet"), then registered with the INT gateway via `/api/vendor-register` (new-vendor path, not `/api/deploy-int`) once self-test passes. Rollback is "stop sending this vendor traffic at the gateway" (a gateway/platform action, out of this repo's reach) — there is no in-repo feature flag; every destructive tool (site/env-var/form/submission/DNS-zone/DNS-record delete, deploy restore) requires explicit `confirm=true` and cannot be triggered by a stray retry, same pattern as every sibling MCP's delete tools.

## Decisions made by DEV01

- **Single `X-Netlify-Token` header, no second resource-identifying header.** Reasoning: Netlify's API is single-tier (one personal access token grants access to everything the token owner's teams can see); there is no per-end-customer resource credential the way Plaid's `access_token` or Hudu's per-instance base URL work. A single header is the simplest credential shape this org's MCPs have used so far, and matches Figma's and Box's single-token convention more closely than Hudu's or Plaid's.
- **`account_id`/`site_id`/`zone_id`/etc. are plain tool arguments, not headers.** Reasoning: these identify *which resource* a call is about, not *who is calling* — the same header-vs-argument split every other MCP in this org already makes (Plaid's `access_token`, Hudu's `company_id`).
- **List tools return `{items, page, per_page, has_more, next_page}` with no `count` field**, unlike Hudu's `{count, page, has_more, next_offset}`. Reasoning: Netlify's API never returns a total result count in any list response body (confirmed against both `docs.netlify.com` and `open-api.netlify.com`); inventing one would mean guessing or making an extra uncounted request per list call. `has_more`/`next_page` are derived from the vendor's own `Link` response header instead, which is the only pagination signal that actually exists.
- **`netlify_restore_deploy` is the only "change what's live" tool in v1; file-upload deploy creation is a Non-goal.** Reasoning: a from-file deploy is a multi-step upload protocol (digest manifest, then per-changed-file PUT), fundamentally different in shape from every other tool here (single JSON-RPC request/response) and not how most Netlify sites are deployed in practice (git integration or a build-hook URL does that outside this MCP's reach anyway). Alternative not chosen: implementing the full upload flow — rejected as disproportionate scope for a first version and a poor fit for the MCP tool-call shape.
- **Env var tools take both `account_id` (required) and an optional `site_id`**, mirroring Netlify's own two-level model exactly, rather than inventing a single "scope" enum. Reasoning: Netlify's own API already expects exactly this shape (`site_id` as an optional query parameter on account-scoped endpoints); reproducing it directly is more predictable for an agent than a custom abstraction over it.
- **Did not adopt any unofficial third-party Netlify Python SDK.** See Tech design → Option analysis.
